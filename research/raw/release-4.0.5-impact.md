# Omarchy v4.0.5 impact on the corpus

Prepared 2026-10-18 by one read-only agent, against the v4.0.4...v4.0.5 compare and upstream's live package databases. This is the evidence behind the 4.0.5 entry in JOURNAL.md, kept for provenance. No verdict here has been applied to the corpus.

Checked afterwards on test2 at omarchy 4.0.5-1, read-only, the same day: `/etc/pacman.conf` lists `[omarchy]` on line 19 above `[core]` on line 21, `/etc/pacman.conf.bak` carries the update's timestamp (00:21), and `quickshell 0.3.2.r7.g2b4501a-1` is installed with packager `Omarchy <pkgs@omarchy.org>`. That moves item 15's install outcome from likely to confirmed, and confirms the reorder and backup overwrite in items 10 and 12 on a real install.

Inputs: compare.json (v4.0.4...v4.0.5, 43 commits as GitHub's compare counts them, 201 files, no truncated patches), the v4.0.5 release notes, PR bodies for #14551, #13048, #11486, #14845, #11925 and omacom/omarchy-pkgs#1231, the v4.0.5 tree, and two live repository databases fetched on 2026-10-18: pkgs.omarchy.org/stable omarchy.db (omarchy-4.0.5-1, omarchy-settings-4.0.5-1, linux-omarchy-7.2.8-9, quickshell-0.3.2.r7.g2b4501a-1, ghostty-1.3.1-3) and stable-mirror.omarchy.org core.db and extra.db (linux-7.2.11.arch1-1, mkinitcpio-42.2-1, systemd-262-1, qt6-base-6.12.0-3, quickshell-0.3.2-1, ghostty-1.3.1-2, easyeffects-8.3.0-1). The workstation is still omarchy 4.0.4-1, linux-omarchy 7.2.5-3. Apart from the test2 checks above, nothing below was observed on a 4.0.5 install.

Tags: confirmed means read in the patch, the package database, or tested with pacman-conf on a scratch copy. Likely means it follows from the patch plus known tool behaviour but was not run on 4.0.5. Speculative means plausible and unread or untested.

Not covered: the bodies of the Hermes and OpenClaw installers (bin/omarchy-install-hermes-cli, bin/omarchy-install-openclaw-cli and their remove scripts) were skipped because no corpus record covers Hermes or OpenClaw beyond the mise items below. The Qt 6.12 `Commons.Color` edits were read only in lock, idle, bar and monitor QML. The October Arch snapshot (mkinitcpio 42.2, systemd 262, pacman 7.1.0.r9, Qt 6.12, PipeWire 1.6.9, linux 7.2.11) was not checked record by record. About 47 records cite older Arch versions, mostly in audit_note.

## 1. Records the release affects

### FIXED-UPSTREAM

1. `nvidia-env-forced-on-igpu-primary-hybrid-laptop` (gpu-drivers, corrected). Driven by #11690, commit 77d5ab8d, files default/hypr/nvidia.lua, bin/omarchy-hw-nvidia-display and migrations/1790282866.sh. nvidia.lua now wraps the variables in `if nvidia_is_display then hl.env("LIBVA_DRIVER_NAME", "nvidia") ... end`, and the new detector exits 1 when `other_boot == 1 && nvidia_boot == 0`, read from sysfs `boot_vga`. The migration runs `omarchy-state set reboot-required` on hybrids, which clears the stale systemd user environment the record's triage condition worried about. Confirmed from the patch. Two caveats belong in the record. The gate is `boot_vga`, not the render node the record's fix tests, so the machines where the dGPU scans out an external monitor are covered only if the iGPU owns `boot_vga` (likely on most hybrids, unconfirmed). `NVD_BACKEND` is still set. The cause's "none has merged as of 2026-09-11" is stale.
2. `omarchy-windows-vm-launch-silent-setgid-chmod` (apps-services, corrected). Driven by #12323, commit 9e31326f, bin/omarchy-windows-vm. Both sites change `chmod 0700` to `chmod u=rwx,go=,a-s`, with the comment "a numeric chmod keeps setuid/setgid on a directory, and dockur marks an initially empty /shared setgid (2777)". A failure now also prints `could not make the VM data directories private`. Confirmed. The fix's "No upstream fix has merged as of 2026-09-11" is stale.
3. `bar-gone-after-update-shell-restart-race` (omarchy-core, corrected). Driven by #11015, commit 9a15267a, bin/omarchy-restart-shell. `timeout 5` becomes `timeout 30`, a new loop waits until `quickshell list -a -j` shows no instance under the config dir, and readiness becomes `deadline=$((SECONDS + 60))` instead of 20 attempts. Confirmed. The cause's "As of 2026-10-05 the latest release is still v4.0.4" is stale.
4. `nvidia-utils-installed-on-amd-intel-only-system` (gpu-drivers, corrected). Driven by #12569, commit d5c55f65, bin/omarchy-install-gaming-steam, which now runs `omarchy-install-gaming-gpu-lib32` before `omarchy-pkg-add steam`. The record already says quattro fixed it and v4.0.4 did not ship it. It shipped in 4.0.5. The cleanup steps still apply to machines that already carry the NVIDIA stack. Confirmed. See also item 25 on provider order.
5. `hyprctl-keyword-monitor-non-legacy-parser` (display-monitors, ok). Driven by #13725, commit d5a02071, shell/plugins/panels/monitor/Panel.qml. The panel now builds `hl.monitor({ output = ..., disabled = true })` and runs `["hyprctl", "eval", expr]`, with the comment "hyprctl keyword is rejected under the Lua config". Only the symptom's display-panel sentence is fixed. `hyprctl keyword` itself is still rejected. Confirmed.
6. `linux-omarchy-intel-iommu-default-on-boot-failures` (boot-kernel, corrected). Driven by omarchy-pkgs#1231 (merged 2026-10-17). The linux-omarchy recipe on omarchy-pkgs master, pkgver 7.2.8 pkgrel 9, has `# CONFIG_INTEL_IOMMU_DEFAULT_ON is not set`, and the stable database lists linux-omarchy-7.2.8-9. The cause's "As of 2026-10-05 the stable repository still ships linux-omarchy 7.2.5-3" is stale. Likely, because the config was read from the recipe and not from an installed /proc/config.gz.
7. `waydroid-no-binder-on-linux-omarchy-kernel` (apps-services, corrected). Same recipe has `CONFIG_ANDROID_BINDER_IPC_RUST=y` and `CONFIG_ANDROID_BINDER_DEVICES=""`, where the record's cause quotes 7.2.5-3 with both binder options off. Likely fixed. A VM test of `waydroid init` would confirm it, and the bad-bindgen failure in the next item could come back if the Omarchy kernel was built against the affected bindgen.
8. `waydroid-rust-binder-no-such-process-bad-bindgen-build` (apps-services, ok). The record says Omarchy's stable mirror "as of 2026-10-04 still serves linux-7.2.3.arch1-3, so omarchy update reports nothing to do". The stable mirror's core.db now lists linux-7.2.11.arch1-1 and linux-lts-6.18.57-2, past the 7.2.4.arch1-2 and 6.18.50-2 rebuilds the record names. Likely fixed for Omarchy's stock-kernel branch.

The cause's "as of 2026-10-04 the omarchy repo still serves 7.2.5-3" is stale (confirmed). Fixed is likely, and needs an affected Intel HDMI machine to confirm.

### FIX-NOW-WRONG

10. `ignorepkg-holdpkg-blocking-upgrade` (pacman-aur, corrected). Driven by #14551, commit e4ba01a7, default/pacman/pacman-stable.conf (also -rc and -edge), which moves `[omarchy]` above `[core]`. The record's hook runs `sudo sed -i '0,/^\[core\]/s||IgnorePkg = linux ...\n\n[core]|' /etc/pacman.conf`. On the 4.0.5 template that line lands inside the `[omarchy]` section. Tested on a scratch copy of the v4.0.5 template: `pacman-conf IgnorePkg` printed nothing and warned `directive 'IgnorePkg' in section 'omarchy' not recognized`. The hold is silently dropped at the next `omarchy refresh pacman` or channel switch. Confirmed. The hook should insert above the first repository or append to `[options]`. Its sentence "`omarchy update` itself does not rewrite /etc/pacman.conf" is also now false once (item 12), although that migration keeps `[options]` lines, so a hold already in `[options]` survives.
11. `webapp-launchers-broken-after-browser-change` (omarchy-core, corrected). Driven by #13520 (3d1d4567) and #14441 (94a8fbc2): bin/omarchy-launch-webapp now runs `browser=$(omarchy-cmd-default-browser)`, and migrations/1791934674.sh writes ~/.config/hyprland-mimeapps.list with `x-scheme-handler/https=omarchy-browser.desktop`. Upstream's own comments say xdg-settings "consults ... the desktop-specific list, which points at omarchy-browser.desktop" and that a set "must only see mimeapps.list". The record's step 1 `xdg-settings get default-web-browser` therefore likely prints `omarchy-browser.desktop` inside the session, and its `xdg-settings set default-web-browser chromium.desktop` likely reports failure even after writing mimeapps.list. Use `omarchy default browser <name>` or `env -u BROWSER XDG_CURRENT_DESKTOP= xdg-settings set default-web-browser <id>`. The cause, which quotes the old script, is stale (confirmed). The behaviour is likely and was not run.
12. `omarchy-update-overwrites-pacman-conf` (pacman-aur, corrected), partly. Driven by #14551 (e4ba01a7, 551f35f0, 27743133), files migrations/1791403252.sh and config/omarchy/hooks/pre-refresh-pacman.d/add-custom-repo.sample. The fix says the sample "inserts `Include = /etc/pacman.d/custom-repos.conf` above `[core]`, so those repos take priority". The 4.0.5 sample uses `0,/^\[omarchy\]/`. Existing installs keep the old copy in ~/.config, since no migration in this release refreshes it (likely). Tested on a scratch copy: the old hook on the new template gives the order omarchy, chaotic-aur, core, so custom repositories now rank below `[omarchy]`. The symptom's "A plain `omarchy update` on Omarchy 4 does not touch /etc/pacman.conf" is false for this release. The migration runs `sudo cp -a /etc/pacman.conf /etc/pacman.conf.bak` and then installs the reordered file, so the single backup that the fix's first step diffs against is overwritten. The danger should say so. Confirmed.

## 3. Changes that suggest new records

1. The repository reorder migration rewrites /etc/pacman.conf, overwrites /etc/pacman.conf.bak, and then runs `omarchy-update-system-pkgs`, a full `-Syu`, inside `omarchy-migrate`. The comment is "Run this even when the config is already ordered so a failed upgrade can be retried". A failed upgrade keeps this migration pending and holds back every later one. Confirmed from the patch. The consequence is likely.
2. Several new migrations exit 1 on purpose and stay pending, which blocks later migrations: 1788996284 ("Update omarchy-nvim to 2026.9.21-2 or newer"), 1789095456 (`mise trust --untrust` failure), 1790017600 (`--retire-mise` cannot remove the environment), 1790397381 ("Update the openclaw package before rerunning"), 1791581004 (boot menu still lacks the parameter) and 1791403252. Confirmed from the patches. A "which migration is stuck and why" record would cover all six.
3. Third-party shell plugins that use a bare `Color` break under Qt 6.12. docs/omarchy-shell.md says "Existing third-party plugins that use bare `Color` must make the same change", and the fix is `import qs.Commons as Commons` with `Commons.Color`. A machine that runs Arch's Quickshell rather than Omarchy's patched build (pinned, or quickshell-git from the AUR) likely loses the shell colours and panels too. Speculative for the second part.
4. Third-party service and panel plugins failing with `Process failed to start ... /scripts/...` on 4.0.3 and 4.0.4 (PR #11925: `__sourceDir` was stripped). Fixed in 4.0.5. Confirmed from the PR body.
5. An idle timeout of 0 locks immediately instead of disabling, up to 4.0.4. Fixed by #12538, where IdleModel.js says "0 means the action is disabled, not fire immediately". Confirmed.
6. Closing the lid during shutdown suspends the machine instead of powering off, up to 4.0.4. Fixed by #13076 with `systemd-inhibit --what=sleep:idle:handle-lid-switch`. Confirmed.
7. The boot sits on a black screen at "Starting Switch Root" until a key is pressed, "about 1 boot in 10". Fixed by #14771 with `systemd.tty.term.console=dumb` and a UKI rebuild migration. Confirmed.
8. A KEF LSX II LT USB speaker locks up after idle (`usb_set_interface -110`), fixed by a WirePlumber rule setting `session.suspend-timeout-seconds = 0`. Speaker tuning host killed when the portal reported a zero realtime budget (`RLIMIT_RTTIME of 0`), fixed by `rtportal.enabled = false`. EasyEffects 8 volume keys moving the EasyEffects sink and not the device, fixed in bin/omarchy-audio-output-sink. All three confirmed from the patches.
9. T2 Macs with macOS wiped get no Wi-Fi firmware, because `apple-bcm-firmware` became `apple-bcm-firmware-fetcher`, which "reads its firmware off an on-disk macOS volume". Dell XPS 13 DX13260 Panther Lake speakers need `linux-firmware-cirrus-dx13260`. Confirmed.
10. Links from apps now go through omarchy-browser.desktop and ~/.config/hyprland-mimeapps.list. Chromium-family browsers get `DefaultBrowserSettingEnabled: false` and Firefox gets `DontCheckDefaultBrowser`, so the browser's own "make default" button is gone. A user who already had http handlers in hyprland-mimeapps.list keeps them and does not get the new routing. Confirmed.
11. Project `bin/` is no longer on PATH under ~/Work (#11336). `rails` now needs `bin/rails`, and a customised ~/Work/.mise.toml has its trust revoked ("Review it before trusting it again"). Confirmed. This also has a security side, see section 5.
12. Hermes is now installed only through Hermes Desktop and updates itself with `hermes update`. OpenClaw moved to a self-updating copy under ~/.openclaw, and its Control UI "Update Gateway" button now works, where the 4.0.4 manual said to skip it. Confirmed from manual/17-ai.md.
13. Smaller items: the calendar grid was wrong in time zones that start DST at midnight (Chile, Cuba), cached Claude usage limits did not reset when their window ended, removing RetroArch left `libretro-database-git` behind, and Wi-Fi QR generation could fail when `ip route get` failed. All confirmed from the patches.
14. Edge and rc users who installed linux-omarchy 7.2.8-8 (a meta package) hit a failing kernel migration until 7.2.8-9 (omarchy-pkgs#1231). Confirmed from the PR body. It touches `kernel-migration-1789325478-no-limine-boot-entry`.

## 5. Security category
